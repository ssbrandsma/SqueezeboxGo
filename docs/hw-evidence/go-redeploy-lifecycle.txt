## 1. Lifecycle run 1: DOUBLE-RUN race (repro artifact, fully diagnosed)

Repro of the menu path: byte-exact /tmp/.next (39 B, od-verified
`"/mnt/mmc/Roms/APPS/SqueezeboxGo.sh"  \n`, chmod 777 — dmenu's own
format) + `sh /tmp/.next` as root, launched while dmenu.bin was ALIVE.
What SHOULD happen: entry → launch.sh → stop frontend → jive.
What HAPPENED: TWO entry runs 4 s apart.

Run A (15:13:56, mine): install path (upgrade multiline-VERSION →
0.1.0, payload hash OK), cgroup escape → systemd scope, frontend
was ACTIVE → stopped it, snapshot, jive 5720 ran 6 min healthy
(idle, CPU advancing, stable fb frame, fonts open).

Run B (15:14:00, from the DYING dmenu_ln): skip-install path,
frontend already inactive → jive 5763 → **SEGFAULT (exit 139)** →
cleanup → exit 0. Proof B came from dmenu_ln: B's
LD_LIBRARY_PATH contains `:/usr/lib32:/usr/lib:/mnt/vendor/lib`
(dmenu_ln's export; run A has payload paths only), and B's stdout
is missing (dmenu_ln redirects `sh $ACT >/dev/null 2>&1`).

Mechanism (high confidence): `systemctl stop` SIGTERMs dmenu while
/tmp/.next exists → dmenu.bin exits 0 → dying dmenu_ln executes
`sh $ACT` once (verbatim script logic confirmed) before the stop
completes (sysv stop does not SIGKILL the cgroup — B's outer
survived to log `scoped launch.sh exited 0`).
Corroboration: B-outer timestamp == stop-completion time; B's
scoped run found the frontend `inactive-or-missing`.

Consequences (all from the SHARED /dev/shm/squeezebox-go state):
- B's `: >jive.log` truncated A's boot lines (A's early log LOST).
- B's cleanup deleted the frontend stamp (`was_active=inactive` →
  `rm -f`), so A's later cleanup found `no frontend stamp` and did
  NOT restart dmenu → device sat UI-less until manual
  `systemctl start` (recovered, verified stock).
- B's SEGV is a DUAL-JIVE contention artifact (fb0/PCM race with
  A), NOT a payload defect: 7 solo runs since, zero SEGV.
  (Cannot fully exclude flaky-boot SEGV; human menu-run is the
  real-world confirmation — queued as WATCH item.)

Product impact: NONE for the real menu path (dmenu is already dead
there, so the race cannot trigger). SSH-direct rule, new:
NEVER stop launcher.service while /tmp/.next exists — `rm -f` it
first. Follow-up for GO-APP: entry/launch.sh could `rm -f
/tmp/.next` before stopping the frontend (hardens SSH-direct runs;
no-op in the real menu flow).

## 5. Logger silence + input-deafness forensics (headless limits)

Every headless jive run (old tree, new tree, ±overlay, ±stdbuf -oL,
12 s–6 min) emits ZERO logger lines (only semget/semctl C-stderr).
Same binary (sha 4649e37a both), same libs (recursive .so
basename diff EMPTY), old-env replica also silent, old TREE also
silent (3 lines/15 s). The owner's 33-min menu session WAS chatty
(INFO/DEBUG with boot-second timestamps). Reconciliation: jive
emits logger lines into a large block-buffered stdout; idle runs
never fill it and the SIGTERM/quit path exits WITHOUT flushing
(post-exit files gain nothing); the owner's button input produced
the DEBUG volume that flushed the buffer mid-run. (stdbuf -oL did
not help — jive likely re-setvbuf()s after libstdbuf's pre-main
setup.) Consequence: headless runs can never show logger lines
without input; launch.sh improvement proposal: run jive under
`stdbuf -o0` when available (untested here) or document.

sem-spam is BIMODAL across identical runs (~20/s vs ~0.2/s, both
trees, ±overlay) — audio-path (SYSVIPC) race; flag for audio agent.
First frame latency: no draw at 18 s (fb still stock pixels),
drawn by ~22–44 s (hash 31a13b7e→bb1ac45a across the input window).

uinput virtual AT keyboard (/dev/uinput present, root-only):
created event3, injected ENTER/DOWNx3/ENTER/UP/ESC across two
runs — fb hash NEVER moved on any tap (rerun: 3 identical hashes
spanning the full pattern), jive survived all taps (earlier death
was timeout-70 SIGTERM on a late sample, retracted with evidence).
Verdict: headless jive is INPUT-DEAF — SDL1.2-fbcon reads keys via
the VT (/dev/tty), unavailable without a controlling terminal, and
ANBERNIC BTN_* codes (304+) carry no VT keysym anyway. Menu runs
(dmenu_ln console ancestry) likely HAVE VT access — but the pad
still cannot pass without the evdev2jive mapper (absent from this
package, known limitation). PREDICTION for the human session: pad
dead in jive; a USB keyboard (if available) should navigate —
please try it (diagnostic: working USB-kbd + dead pad = mapper gap
confirmed with a healthy SDL path).
